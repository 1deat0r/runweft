# Runweft protocol contract v1.0

Status: Ticket 01 contract implementation complete locally (2026-09-29), following independent systems, security, and evaluation closure reviews. This document and `schemas/run-protocol.schema.json`, `schemas/lifecycle-transitions.json`, `schemas/error-policy.json`, and `schemas/peer-policy.json` define data and validation behavior only. They do not implement a coordinator, scheduler, durable store, broker, production IPC listener, provider adapter, or effect executor.

## Schema and toolchain

- `schemas/run-protocol.schema.json` is the canonical JSON Schema Draft 2020-12 wire schema.
- `schemas/lifecycle-transitions.json` is the canonical transition allow-list, guard, retry, reconciliation, and durable-event mapping.
- `schemas/error-policy.json` defines retry advice; `schemas/peer-policy.json` defines authenticated peer roles and message direction.
- `npm run generate` runs the scaffold status generator and protocol generator. The protocol generator creates Rust bindings with `quicktype-core` 26.0.0 and TypeScript bindings with a deterministic repository-local emitter, plus transition allow-lists and `docs/protocol-transitions.md`. The quicktype TypeScript backend overflows on the recursive extension type, so the local emitter preserves that recursive alias without another dependency.
- Rust `jsonschema` 0.58.2 and TypeScript Ajv 8.20.0 with date-time format support independently validate the same source schema. Both reject unknown properties outside `extensions`. Generated types never establish that untrusted input is valid.
- Schema validation is followed by shared semantic checks for exact integer maxima, authenticated peer authority, lease ownership, receipt linkage, digest binding, and raw UTF-8 limits. JSON Schema or generated types alone are not a complete protocol validator.
- Schema, policy, generated-binding, and generated-doc drift are part of `npm run check`; exact dependency versions are locked. Generation and validation are offline after dependencies are installed.

## Bounded input and wire compatibility

Before JSON parsing, validators reject raw messages larger than 1 MiB, duplicate object keys, and nesting deeper than 32 containers. UTF-8 byte input is strict: a leading BOM and strings or keys containing unpaired surrogate escapes are malformed. Protocol v1 contains no JSON number tokens: counters, amounts, and extension numeric data are strings. Extension strings are limited to 4096 UTF-8 bytes; nested extension keys are limited to 128 UTF-8 bytes. These are v1 limits for the validation boundary, not production transport limits.

Every message has `protocol_version: "1.0"`. V1 supports exactly that version; other string versions return `unsupported_version` before payload validation. Missing or non-string versions are `malformed_payload`. There is no negotiation or automatic rewriting of old commands.

Envelope objects are closed. Unknown properties outside `extensions` return `unknown_field`. All ordinary variants are critical: a recognized message kind with an unrecognized variant returns `unknown_critical_variant` before payload validation. Unknown message kinds return `malformed_payload`.

The cross-language extension subset is JSON null, booleans, strings, arrays, and objects. JSON numbers are rejected; encode numeric values as strings to preserve them exactly across languages. An `extensions` object has at most 32 reverse-domain namespaced keys. Nested extension objects have at most 32 properties per level, keys at most 128 UTF-8 bytes, and string values at most 4096 UTF-8 bytes. Extension data is preserved exactly as JSON values and is ignored for authorization, routing, lifecycle, and effect decisions.

Identifiers are opaque bounded strings. Coordinator generations, event sequences, lease epochs, and micro-USD amounts are canonical unsigned decimal strings, never JSON numbers. Leading zeroes are invalid except for zero itself. Validators enforce numeric maxima using exact integer parsing: unsigned 64-bit values are at most `18446744073709551615`; micro-USD values are at most `340282366920938463463374607431768211455`. `coordinator_generation`, `sequence`, and `epoch` are positive; `lease_epoch` is positive; budget amounts may be zero. These exact maxima are a required post-schema check because the portable string patterns only bound lexical shape and digit count.

## Authenticated peer, scope, and command identity

The authenticated peer identity and role come from the transport/session, never from message fields. `schemas/peer-policy.json` is authoritative for direction and per-variant roles. Users may submit user commands; workers may submit only `attempt.result.submit`; reconciliation peers may submit only `effect.reconciliation.propose`. A worker result is accepted only when the authenticated peer ID equals the assigned subject on the coordinator-owned current lease, in addition to an exact scope/lease tuple match. The result's `run_id`, `task_id`, and `attempt_id` must each match both the claimed lease and current lease. A missing current lease or any tuple/ID mismatch returns `stale_lease`; a different authenticated worker returns `unauthorized`. Durable events, responses, and protocol errors are accepted only from the authenticated coordinator. A worker result is a proposal command, not a durable event.

The coordinator alone authors durable state events. `actor` records the authenticated cause that the coordinator accepted and recorded; it is historical provenance, not proof supplied by the event sender. A client or worker cannot create authoritative state by sending an event or by claiming `actor.kind: "coordinator"`.

Every command and event is scoped to `profile_id`, `project_id`, `profile_incarnation`, and `coordinator_generation`. Event records also carry `event_id`, `run_id`, per-run `sequence`, `causation_id`, `actor`, `graph_revision_id`, `policy_revision_id`, and `observed_at`. An attempt result carries a lease binding to profile, project, run, task, attempt, lease ID, profile incarnation, coordinator generation, and epoch. These fields are claims to compare against coordinator-owned authority; they are not credentials.

Command identity is `(profile_id, project_id, profile_incarnation, command_id)`. Its intent projection includes `protocol_version`, `kind`, `variant`, `profile_id`, `project_id`, `profile_incarnation`, `payload`, and `extensions`. Comparison is recursive JSON structural equality: object key order is ignored, array order and every value are significant. The coordinator generation is excluded so a client can refresh it after ordinary owner replacement; extensions are included so the same ID cannot hide a changed request. For an authenticated peer in the matching incarnation, an existing ID with the same projection returns the original durable result before stale-generation rejection. Reuse with a different projection returns `conflict`. A fresh command must then pass current-generation, lease, role, policy, and lifecycle checks. This ordering permits recovery of an acknowledged result without re-executing a command.

The command identity, intent projection, original result, and every event produced by a state-changing command commit atomically. If that transaction fails, none of those records is durable; if it commits and the response is lost, replay returns the saved result without adding events. Keep deduplication records for the full lifetime of the profile incarnation. Retire an incarnation with a durable fence before purging its records, so a delayed command from that incarnation is rejected before lookup or execution. Owner replacement uses a durable monotonic generation allocator scoped to the same profile, project, and incarnation. A generation is never reused or wrapped; if the unsigned 64-bit maximum is reached, ownership cannot move to a new generation and allocation returns `resource_exhausted`.

## Lifecycle, events, and recovery

Every transition in `schemas/lifecycle-transitions.json` has a coordinator guard and maps to its durable event variant. Every other state pair is invalid. The generated `can_transition` allow-list does not evaluate guards; only a future coordinator can establish their required evidence. Graph revision validation, rejection, admission, and supersession all have event representation. Initial `run.admitted` is the Run creation event.

The table includes cancellation from an admitted Run before any attempt exists and from a queued Task before dispatch. Cancellation prevents future admissions; it does not claim to undo an upstream action already accepted.

Effect state transitions are explicitly fenced. Before calling a tool, the coordinator rechecks the current lease, approval, deny rules, grant validity, and target, then durably commits the `authorized → invoking` event and confirms that commit before crossing the external effect boundary. A failed or uncertain commit means no call is made until durable state is reread. On recovery, any committed `invoking` intent without a terminal receipt is conservatively moved to `unknown_effect`, even if the crash may have happened before the tool call. That intent is never called again. Approval binds `action_id`, `target_id`, `artifact_digest`, `grant_revision_id`, and `policy_revision_id`. `action_digest` is SHA-256 over these fields using this byte preimage, in exactly this order:

1. UTF-8 bytes `runweft.effect-approval.v1` followed by one zero byte.
2. For `action_id`, `target_id`, `grant_revision_id`, and `policy_revision_id`, in that order: a 4-byte unsigned big-endian byte length, then the UTF-8 field bytes.
3. The 32 raw bytes decoded from lowercase hexadecimal `artifact_digest`.

The intent and approval must each recompute to the same digest and match every bound field. Current deny rules, grant validity, target, and lease are rechecked immediately before the effect boundary. `effect.reconciliation.propose` carries a claim and evidence reference only. A coordinator may emit `effect.reconciled` only after an independent evidence verifier establishes the outcome for that exact intent; `outcome: applied` must pair with `to_state: reconciled_applied`, and `outcome: not_applied` with `to_state: reconciled_not_applied`. The event repeats the intent digest, target, artifact, lease, source, and evidence digest. Missing, untrusted, mismatched, or unresolved evidence leaves the intent in `unknown_effect`. The original intent is never replayed after invocation may have begun. A separately recorded intent with fresh explicit authorization is required for any later action, even if evidence proves the prior action was not applied.

Attempts are immutable. Retry creates a new attempt. An unknown external outcome blocks dependent work until independent reconciliation. An artifact result is accepted only for the exact active lease and authenticated assigned worker; the coordinator-authored `attempt.state.changed` event to `verifying` embeds the accepted result ID, exact artifact digest, and lease binding. The Attempt `verifying → succeeded` event embeds the immutable verification receipt ID, verifier ID, evidence digest, and same artifact digest. The Task `verifying → succeeded` event must carry that exact `attempt_id` and `verification_receipt_id`; replay links Task success to the matching succeeded Attempt event and receipt. An effect `invoking → applied` event embeds the immutable effect receipt with exact intent/action/target/artifact/lease and evidence source/digest. An `invoking → failed` event embeds the independent evidence reference proving no effect was applied. Event replay therefore retains the accepted artifact and effect proof references. Receipt mismatches block the transition.

Artifact, verification receipt, effect receipt, and reconciliation evidence references are immutable within a profile incarnation and are bound to their content digest. Their metadata and referenced content remain resolvable while that incarnation is active and its events can affect current state. Missing or mismatched evidence cannot satisfy a transition and leaves the affected state pending or `unknown_effect`. Archive retention after incarnation retirement is a separate product policy; a production durable replay design must choose that retention period before implementation.

Per-run event sequences are unique and strictly increasing across coordinator generations; owner replacement never resets a run's sequence. Sequence exhaustion is a `resource_exhausted` failure before commit and never wraps. Every accepted state-changing command commits at least one event. `command.accepted.event_sequence` is the highest event sequence committed by that command. An idempotent retry returns the original sequence cursor.

## Validation and caller-visible errors

Both language validators return the same normalized result: either `{ "status": "accepted", "message": <unchanged JSON value> }` or `{ "status": "rejected", "code": <stable code> }`. Every accepted fixture pins the complete unchanged message as its expected value. V1 does not emit field pointers. Errors never echo input fields, credentials, provider bodies, paths, stack traces, or current coordinator state. A wire `protocol.error` contains only `correlation_id` and an error code. A rejected response echoes its command ID and error code; scope fields on ordinary responses echo the request only.

If several conditions fail, select the result by this order:

1. Raw size/depth limit: `resource_exhausted`; then JSON parsing or wrong top-level type: `malformed_payload`.
2. Missing/non-string version: `malformed_payload`; unsupported string version: `unsupported_version`.
3. Unknown kind: `malformed_payload`; unknown variant for a known kind: `unknown_critical_variant`.
4. Closed-schema unknown property: `unknown_field`; otherwise schema/type/format/range failure: `malformed_payload`.
5. Authenticated peer role or profile/project mismatch: `unauthorized`; profile incarnation mismatch: `stale_profile_incarnation`.
6. For commands, authenticated duplicate identity lookup; same projection returns the saved result and a different projection is `conflict`.
7. Current coordinator generation mismatch: `stale_coordinator_generation`; lease mismatch: `stale_lease`.
8. Approval, evidence, policy, and state checks: `unauthorized`, `requires_confirmation`, `unknown_effect`, or `invalid_state_transition` as defined by the failing policy. A missing referenced entity is `not_found`.

The stable error union is `unsupported_version`, `unknown_critical_variant`, `malformed_payload`, `unknown_field`, `stale_profile_incarnation`, `stale_coordinator_generation`, `stale_lease`, `invalid_state_transition`, `conflict`, `not_found`, `unauthorized`, `resource_exhausted`, `requires_confirmation`, `unknown_effect`, and `internal`. Retry advice is not a wire boolean; clients derive it from `schemas/error-policy.json`. Only `resource_exhausted` is automatically retryable after its declared limit window, with the same command ID and intent projection. A stale-generation response requires an explicit fresh handshake and then a same-ID replay; it is not a blind retry. All retries still require current authentication and authority. An uncertain effect is never made retryable by this table.

## Deterministic fixture oracle

`tests/fixtures/protocol/v1/cases.json` is a checked-in, literal oracle of exactly 50 stable cases. Each case contains its input, authenticated peer/current authority context, expected accepted or rejected result, and category. Expected outcomes are hand-derived from this frozen contract, not emitted by either implementation. A variant coverage map points every schema-known command, event, response, and error variant to a positive fixture in the main or behavior corpus. Rust and TypeScript independently run the same fixtures and compare their normalized output with the literal expectation; implementation agreement alone does not pass.

Category allocation is exact: 12 valid messages/transitions; 8 version and version-boundary cases; 8 malformed, type, unknown-field, and numeric-range cases; 6 accepted extension cases; 6 rejected unknown critical variants; 5 stale profile-incarnation cases; and 5 stale coordinator-generation/lease cases. Numeric cases include u64 and u128 maximum and maximum-plus-one boundaries, zero, and leading zeroes. Extension cases preserve exact numeric strings and reject JSON numbers. Authority cases cover forged coordinator events, worker-submitted state changes, stale incarnations/generations/leases, and cross-attempt lease reuse.

A separate exhaustive deterministic check enumerates every state pair for every entity in the lifecycle source. It accepts exactly the listed transitions, rejects every unlisted pair, and checks that each edge's event variant exists in the protocol schema. `tests/fixtures/protocol/v1/behavior-cases.json` adds literal validator trust-boundary cases for peer roles and actor forgery, worker lease bindings, approval digest mutations, and extension preservation, plus contract vectors for command replay/atomicity, generation allocation, event cursors, crash recovery, receipt linkage, and evidence matching. The latter vectors are checked by small test models and fixture relationships; they do not exercise a coordinator, transactional store, or crash recovery implementation. `raw-cases.json` pins duplicate-key bytes, exact size/depth boundaries, UTF-8 extension key/value boundaries, BOM and Unicode rejection, and 32/33-property boundaries for top-level and nested extension objects. For the 1 MiB cases, the fixture stores a literal UTF-8 prefix and a repeated single-byte space count; each harness constructs the same bytes and verifies the pinned length and SHA-256 before validation. These checks supplement, and do not inflate, the 50-case oracle.

## Fake effect harness and limits

The test-only effect model uses an in-memory provider stub that proposes one fixed action and a fake tool that records the exact `effect_intent_id`, action, target, artifact digest, grant revision, policy revision, action digest, and fenced lease it receives. `behavior-cases.json` pins the proposed action, invocation record, successful result/receipt, pre-invocation rejection, and ambiguous-timeout/repeat outcomes. These assertions describe the contract model only; they do not demonstrate that a future coordinator persists the ordering or recovers safely. The approved model path returns the fixed receipt and records one invocation. A mismatch, stale authority, forged event, or missing approval records zero invocations. An ambiguous fake timeout after invocation records one invocation, sets `unknown_effect`, and a repeated request for the same intent is refused without a second invocation. No test contacts a provider, reads credentials, opens production IPC, persists state, invokes a process, or enables execution in the CLI/daemon.

The local socket-pair probe is an isolated test prototype for framing, validation, and round-trip overhead. `docs/protocol-ipc-measurement.md` records payload sizes, host/tool versions, warmups, repetitions, p50, and p95. It is not a production IPC, runtime, or performance claim.
