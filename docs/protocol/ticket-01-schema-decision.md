# Ticket 01 protocol schema and contract decision

Status: **proposal for frozen board review, round 1**  
Ticket: [#4](https://github.com/1deat0r/runweft/issues/4)  
Owner authorization: 2026-09-28  
Implementation is not approved by this proposal; the five-seat board must vote on this frozen text before protocol bindings are generated.

## Decision requested

Approve the V1 schema source, compatibility and validation rules, versioned envelope fields, transition contract, error union, code-generation workflow, and test boundaries below. This is a contract decision for future clients and stored records. It does not implement scheduling, persistence, dispatch, IPC service endpoints, provider access, or tool execution.

## 1. Schema source and toolchain

- `schemas/runweft-protocol-v1.schema.json` is the sole normative V1 wire-data schema. It uses the JSON Schema Draft 2020-12 dialect and local `$defs` only. No network or filesystem `$ref` resolution is allowed.
- Its canonical identifier is `urn:runweft:protocol:v1`; the application wire integer remains `protocol_version: 1`.
- JSON Schema validates wire values. `typify` 0.8.0 generates Rust data types; `json-schema-to-typescript` 16.0.0 generates TypeScript declarations. The generated bindings are checked in and regenerated through `npm run generate`. Rust and npm lockfiles pin the generators and runtime validators.
- Ajv 8.20.0 validates TypeScript-side wire values in strict mode. Rust `jsonschema` 0.58.1 validates Rust-side wire values with remote/file resolution disabled. Neither validator coerces values, inserts defaults, strips fields, or invokes custom network retrieval.
- Generated language types are ergonomic representations, not proof of full JSON Schema validity. Both language boundaries validate the original JSON value against the canonical schema before deserialization/use. This is required because type generation does not encode every range/conditional constraint.
- The existing `runtime-status.schema.json` remains the separate, constant-only scaffold-status schema. Its bindings stay generated by the narrow current generator. The new V1 contract is not advertised as a production schema compiler or running service.
- Keep the schema within a reviewed subset that all selected tools exercise in fixtures: `$defs`/`$ref`, `oneOf`, `const`/`enum`, primitive types, `required`, `properties`, `additionalProperties`, and bounded arrays/strings/integers. `format` remains annotation unless the shared semantic layer defines and tests its exact assertion. Custom lifecycle and decimal-string rules live in a short, paired Rust/TypeScript semantic validator and are covered by golden fixtures.

References: [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12), [Ajv Draft 2020-12 support](https://ajv.js.org/json-schema.html), [jsonschema Rust validator](https://docs.rs/jsonschema/0.58.1/jsonschema/), [Typify](https://docs.rs/typify/0.8.0/typify/), [json-schema-to-typescript](https://github.com/bcherny/json-schema-to-typescript).

## 2. Version and unknown-data policy

- Every envelope carries integer `protocol_version: 1`. V1 implementations accept exactly version 1. Missing, fractional, or wrong-typed values reject as `PROTOCOL_SCHEMA_INVALID`; any other integer rejects as `PROTOCOL_VERSION_UNSUPPORTED`. A small version precheck runs before general schema validation so both languages return the same code.
- Envelope and payload objects reject unknown direct properties. This catches misspellings and avoids silently accepting authority-bearing fields.
- Forward-compatible optional data belongs in an explicit `extensions` map. Each entry is `{ "critical": boolean, "value": <JSON value> }`. Unknown non-critical entries are accepted and preserved as opaque data. Unknown critical entries reject with `UNKNOWN_CRITICAL_VARIANT`. There are no registered extension names in V1; later registrations require a reviewed schema/version update and fixtures.
- Unknown `message_type` values always reject as `UNKNOWN_CRITICAL_VARIANT`. A sender cannot mark a command or event variant optional. Unknown optional data is only possible through `extensions`.
- Schema and protocol version changes are independent. A new JSON Schema generator or validator release does not change the wire protocol. A breaking wire change increments `protocol_version`; V1 readers never reinterpret a future major value.

## 3. Envelope and value conventions

All messages have `protocol_version`, a message UUID, a discriminated `message_type`, `profile_id`, `profile_incarnation`, `project_id`, and a typed body. Commands also carry a scoped `command_id` and optional expected revision. Responses and errors identify the command they answer. Events carry `event_id`, `run_id`, per-run `sequence`, `causation_id`, `actor`, `graph_revision`, `policy_revision`, and `observed_at`.

V1 `message_type` variants and body contracts are finite and versioned:

- Commands: `command.graph.submit` carries `run_id`, optional `based_on_revision_id`, and `graph_revision` (`graph_revision_id`, tasks with `task_id`, `depends_on`, `required`, and SHA-256 `content_digest`). `command.run.pause`, `command.run.resume`, and `command.run.cancel` carry `run_id` and `expected_run_revision`. `command.task.retry` carries `run_id`, `task_id`, `expected_task_revision`, and `previous_attempt_id`. `command.events.replay` carries `run_id`, optional `after_sequence` (absence means the beginning), and `page_size` from 1 through 1,000.
- Events: `event.run.state_changed`, `event.graph_revision.state_changed`, `event.task.state_changed`, `event.attempt.state_changed`, and `event.effect.reconciliation_required`. State events carry the object ID, old/new state, and resulting revision; attempt events carry the lease binding; reconciliation events carry the effect classification and a stable reason code. `actor` is one of `user`, `coordinator`, `model`, `worker`, `provider_adapter`, or `broker`; only the coordinator may authoritatively emit lifecycle changes. Other actors identify proposals or evidence and never grant authority.
- Responses: `response.command_recorded` (command ID, resulting revision and event sequence) and `response.events_page` (events and resume cursor). In a future durable implementation, `command_recorded` is only sent after its transaction commits, as required by S2 DUR-01; this schema does not add such a handler.
- Errors: `error.command_rejected` with the stable error object in §5. `message_id` is the event ID for events, avoiding two competing event identities. A response or error includes `in_reply_to_command_id`.

The top-level schema is closed to unrecognized direct properties. Each body has a dedicated `$defs` schema. A frame is UTF-8 JSON, at most 1 MiB, at most 32 nested containers, with at most 32 extension entries; receivers reject over-limit data before semantic validation. These bounds constrain future transports and do not create a transport endpoint now.

- UUIDs are lower-case hyphenated strings; they are opaque identifiers, not authority by themselves.
- Integers that may exceed JavaScript's safe range, including sequence/generation/fencing counters and money in integer micro-USD, use canonical unsigned decimal strings (`0` or a non-zero digit followed by digits; no sign, decimal point, exponent, or leading zero). The schema bounds these strings to 39 digits; the shared semantic validator also checks the exact unsigned 128-bit maximum (`340282366920938463463374607431768211455`). Money is an integer count of micro-USD and every estimate/actual is bound to a `price_table_revision`. Human-readable model/provider amounts are never accumulated as floating point in the protocol.
- `profile_incarnation` identifies one profile history. Ordinary restart preserves it; restore/rollback creates a fresh unpredictable value. A command is scoped by `(profile_id, profile_incarnation, command_id)`. The coordinator calculates a SHA-256 digest over RFC 8785 canonical JSON for the command type, protocol version, scope, expected revision, and body; it excludes transport/message IDs and timestamps. Repeating a command ID with a different digest yields `COMMAND_ID_CONFLICT`; durable idempotency storage belongs to Ticket 02.
- A lease contains `lease_id`, `attempt_id`, the same `profile_incarnation`, `coordinator_generation`, a monotone `fencing_token`, and an RFC 3339 expiry. Any mismatch is rejected before an effect boundary. This ticket defines the binding; it does not implement that boundary.
- Time values use a canonical UTC profile of RFC 3339: exactly `YYYY-MM-DDTHH:mm:ss.sssZ`, with calendar/range validation and no leap-second spelling. Rust and TypeScript include the same boundary cases; local times, offsets, and variable precision are rejected.
- Events are ordered only by per-run `sequence`, never by wall time. `actor`, `causation_id`, graph/policy revisions, and observed time are provenance, not permission grants.

## 4. Lifecycle contract

The schema defines state names and message shapes; a pure Rust/TypeScript transition validator checks the following table. It does not mutate durable state. A transition request cannot itself establish that its guard was satisfied. The transition validator takes `(object kind, current state, requested next state, guard facts)` and returns a stable error code; event sequence ordering is checked separately.

| Object | Allowed transitions | Guard and ownership rule |
|---|---|---|
| Run | States: `draft`, `awaiting_approval`, `queued`, `running`, `paused`, `cancelling`, `succeeded`, `failed`, `cancelled`, `unknown_effect`. `draft → awaiting_approval/queued/failed/cancelled`; `awaiting_approval → queued/failed/cancelled`; `queued → running/failed/cancelled`; `running → paused/cancelling/succeeded/failed/unknown_effect`; `paused → running/cancelling/cancelled`; `cancelling → cancelled/failed/succeeded/unknown_effect`. Terminal states have no outgoing transition. | Coordinator owns transitions. `queued` requires a valid graph revision and authorization/budget admission. `succeeded` requires every required task accepted. `cancelled` requires no unresolved effect. `unknown_effect` blocks dependents and automatic retry. |
| GraphRevision | States: `proposed`, `validated`, `active`, `rejected`, `superseded`. `proposed → validated/rejected`; `validated → active/rejected`; `active → superseded`. Terminal states have no outgoing transition. | Revisions are immutable. Activation requires deterministic graph validation and coordinator admission. Any amendment creates a new revision; an active revision is never edited in place. |
| Task | States: `blocked`, `ready`, `running`, `verifying`, `awaiting_approval`, `paused`, `cancelling`, `succeeded`, `failed`, `cancelled`, `skipped`, `unknown_effect`. `blocked → ready/cancelled/skipped`; `ready → running/awaiting_approval/cancelled/skipped`; `running → verifying/awaiting_approval/paused/cancelling/failed/unknown_effect`; `verifying → succeeded/ready/failed/unknown_effect`; `awaiting_approval → ready/failed/cancelled`; `paused → running/cancelling/cancelled`; `cancelling → cancelled/failed/succeeded/unknown_effect`. Terminal states have no outgoing transition. | Coordinator owns eligibility, state changes, and acceptance. Dependencies become ready only after required outputs are accepted. `skipped` is allowed only for optional tasks under the graph's completion policy. `succeeded` requires an accepted receipt. Retry creates a new Attempt; it never reopens or overwrites an old Attempt. No model, provider, worker, or reviewer can self-accept. |
| Attempt | States: `created`, `admitted`, `running`, `verifying`, `succeeded`, `failed`, `cancelled`, `unknown_effect`. `created → admitted/cancelled`; `admitted → running/cancelled`; `running → verifying/failed/cancelled/unknown_effect`; `verifying → succeeded/failed/cancelled/unknown_effect`. Terminal states have no outgoing transition. | The coordinator creates and fences attempts. Inputs, grant, model/config, and lease are immutable for an attempt. An ambiguous external effect stays `unknown_effect` until a separate reconciliation result is recorded; it is never replayed just because acknowledgement was lost. A retry is a new Attempt after the previous attempt has a retryable, reconciled outcome. |

Pause/cancel/approval are explicit states or transitions rather than inferred from transport closure. State transition messages include expected current state/revision so conflicting proposals fail with `REVISION_CONFLICT` or `TRANSITION_NOT_ALLOWED`. An effect that completes after cancellation may be recorded as succeeded only if its receipt was accepted before the cancel transition wins; otherwise it remains a reconciliation question. Retry/reconciliation mechanics, persistence, and actual effect admission remain Ticket 02 or later.

## 5. Caller-visible error union

The stable machine-readable codes are `PROTOCOL_VERSION_UNSUPPORTED`, `PROTOCOL_SCHEMA_INVALID`, `UNKNOWN_CRITICAL_VARIANT`, `STALE_PROFILE_INCARNATION`, `STALE_COORDINATOR_GENERATION`, `LEASE_BINDING_INVALID`, `COMMAND_ID_CONFLICT`, `REVISION_CONFLICT`, `TRANSITION_NOT_ALLOWED`, `NOT_FOUND`, `POLICY_DENIED`, `APPROVAL_REQUIRED`, `BUDGET_EXCEEDED`, `DEADLINE_EXCEEDED`, and `INTERNAL`. Each error includes a request/command correlation ID, `retryable`, and a sanitized optional JSON Pointer; human-readable text is non-normative and must not contain credentials or private payloads. Stale incarnation, generation, invalid lease, unknown critical variant, schema failure, policy denial, and invalid transition are non-retryable without a new authorized request. Internal details are not returned over the protocol.

## 6. Fixtures, adapters, and experiment limits

The 50 shared fixtures follow the allocation in issue #4. Each fixture has a stable ID/category, wire input, expected accept/reject result, expected normalized JSON for acceptance, and exact stable error code for rejection. Rust and TypeScript independently execute every fixture against the expected file; a separate check confirms both implementation result sets agree. Unknown non-critical fixtures prove `extensions` preservation; all unknown variant / critical-extension fixtures reject before any effect. Stale incarnation/generation/lease fixtures reject at protocol validation.

A test-only harness may pass a fixed input through fake provider and fake tool functions and count in-memory stub invocations. This test does not add provider/tool APIs to production packages. Rejected or unauthorized requests must leave the counter at zero; one fixed, authorized fixture may complete a fake round trip. The default CLI and daemon remain execution-disabled.

Any IPC experiment is an explicitly named Rust `UnixStream::pair()` prototype with no filesystem socket, daemon, credentials, or provider. It compares in-memory JSON encode/decode with local socket-pair round trips at fixed payload sizes, after documented warmups and repetitions, and reports p50/p95 plus host and tool versions. Results characterize only this prototype and do not claim production IPC performance or satisfy EP1 operational gates.

## 7. Required board questions

Reviewers should challenge: (a) whether JSON Schema 2020-12 plus separate validators/type generators creates a single-enough source of truth; (b) whether accepting only unknown non-critical data through `extensions` and failing closed on unknown variants/critical extensions is explicit and safe; (c) whether the envelope/fencing/idempotency fields preserve S2 authority boundaries; (d) whether the lifecycle transition/guard table is testable without accidentally claiming persistence or execution; and (e) whether the test harness/IPC prototype can be mistaken for production capability.
