# Runweft: a successor to oh-my-openagent

Design revision: **r2**. Research date: **28 September 2026**. Status: **unanimously approved for implementation and testing by all five AI board seats**. Round history: r1 two BUILD / one REJECT / one CONDITIONAL; r2 five BUILD. This is a design and delivery plan, not an implemented or benchmarked runtime.

## 1. Recommendation and scope

I would build **Runweft**, a local-first runtime for completing engineering tasks with durable state, constrained execution, and evidence attached to every completion. Its central unit is a **run**, containing a versioned task graph, attempts, permitted actions, budgets, workspace snapshots, and verification receipts. A conversation is one interface to that run.

Use a **Rust execution core**, **TypeScript integrations and interfaces**, **SQL persistence**, and **Python offline evaluation**. Start with a modular monolith and isolated worker processes. Add remote workers only after the local contract works. Do not start with Kubernetes, a distributed message bus, a custom model, or a marketplace.

The differentiator is a consistent contract: each interface and adapter must agree about what was authorized, what was attempted, what changed, what was verified, and what can safely resume. Faster code alone will rarely compensate for extra model calls or poor context selection. Rust is an implementation choice for the trusted core, not a claim of better model intelligence or guaranteed security.

Target users initially: individual developers and small teams running long coding tasks on one workstation or an explicitly selected remote Linux worker. Preserve useful OmO concepts—specialist roles, curated skills, model routing, CodeMode, workspace isolation, recoverable DAGs—while narrowing the number of places that can own consequential state.

**Date discipline:** the inspected default branch is `dev`, commit `713775cedd533d00c2048ec6dc677f942f3b2ad0`, committed 2026-09-28 14:31:05 +09:00. Root and `omo-ai` package manifests say **5.0.1**. This is an inspected source snapshot, not proof that every feature was available in every published installation. 2027 is a planning horizon; no future model, protocol, performance gain, or release is assumed.

The source tree also retains OpenCode and Codex integrations and numerous shared core packages. The older plugin architecture remains relevant to those adapters, but is not the whole product. ## 3. Languages: what goes where and why

| Aspect | Language / implementation | Reason, benefit relative to OmO, and tradeoff |
|---|---|---|
| Run state machine, scheduler, budgets, cancellation | **Rust**, stable toolchain, Tokio for bounded asynchronous I/O | Algebraic enums make legal states explicit; ownership helps manage tasks, resources and cancellation. One core standardizes lifecycle authority across supported adapters; OmO already shares substantial core code. Rust has a higher learning and compilation cost. Ownership does not prove business invariants. |
| Capability broker, process supervisor, workspace operations | **Rust**; small audited OS bindings | Process lifetime, file handles, resource accounting and path containment belong near the operating system. Core boundaries stay reviewable. Minimize unsafe code and inventory FFI; native libraries remain part of the trusted computing base. |
| CLI and first TUI | **Rust**, clap and Ratatui | Ship a native entry point using the same protocol client as the web UI. Useful for SSH, CI and offline operation. Structured JSON output remains available; terminal output from tools is escaped. This adds UI work, so begin with plain CLI before a rich TUI. |
| Web run inspector and editor extension | **TypeScript**, React, semantic HTML and CSS | The web and editor ecosystems make diffs, timelines, accessibility, search and interaction easier to develop. UI renders projections and sends commands; it cannot set a run to completed. Prefer an ordinary local browser UI first; a Tauri shell is optional later. |
| Model provider adapters, MCP/ACP bridges, extension SDK | **TypeScript**, a pinned supported **Node LTS** runtime | Fast access to provider SDKs and familiar plugin authoring. Run each trust domain in a supervised extension process with quotas and explicit capabilities. This keeps OmO's TypeScript ecosystem advantage while moving durable authority outside it. Node is a support choice; Bun remains optional development tooling after compatibility tests. |
| CodeMode programs authored by agents | **Restricted JavaScript**, optionally TypeScript transpiled before evaluation | Preserve concise loops and batched independent tool calls. Execute in a disposable OS-isolated worker; brokered API handles are the only effect path. A JavaScript VM or Node `vm` context alone is not a security boundary. Each nested call still gets its own authorization, budget and receipt. |
| Portable bounded plugins, later | **Rust to WebAssembly**, WIT interfaces with Wasmtime | Suitable for deterministic transforms, filters and small computation extensions. Host imports explicitly grant capability; fuel/time/memory limits bound work. Do not require browser drivers, Python science tools, or arbitrary npm packages to fit Wasm. Wasm does not sandbox native processes started outside it. |
| Persistence and retrieval | **SQL** migrations and queries, called from Rust; SQLite initially | Transactions fit attempts, leases, reservations and evidence better than many independent JSON documents. FTS provides an initial search index. PostgreSQL is a later alternative deployment backend, not another mandatory local service. SQL is the data language, not an orchestration DSL. |
| Offline evaluations, trace analysis, routing experiments | **Python**, typed datasets, pytest, scientific libraries | Strong statistics and analysis tooling without making Python an end-user runtime dependency. Evaluation outputs become versioned data; notebooks do not execute inside the authority process. |
| Schemas, configuration, prompts and skills | **JSON Schema**, TOML, Markdown | Schemas generate Rust/TypeScript clients and Python data validators. TOML is human configuration; Markdown carries skills with typed manifests. These are data formats, not extra production programming languages. Never execute arbitrary configuration code. |
| Build, releases, infrastructure | **Rust cargo-xtask** plus small TypeScript scripts; minimal shell; YAML CI | Reuse the two production languages and keep platform shell code thin. Package signatures, SBOMs and migration checks are release products. Add infrastructure-as-code only when the remote deployment exists. |

Rust's ownership model provides memory-safety benefits without a garbage collector; it does not prevent authorization mistakes or races between external systems. [Rust ownership](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html). Wasmtime's security depends on the imports made available by the host. [Wasmtime security](https://docs.wasmtime.dev/security.html). Choose a supported Node LTS line at release time and pin its patch version; do not infer that this machine's Node version is the production baseline. [Node release policy](https://nodejs.org/en/about/previous-releases).

**Why not all TypeScript?** It is a viable first prototype and would reduce staffing needs. The reason to split is a long-lived, privileged, resource-managing core with stable semantics, not a presumed inability to implement durability in TypeScript. **Why not all Rust?** Providers and plugins change too quickly to justify forcing every contributor into Rust. **Why not Go as well?** Go could replace Rust if the team is substantially better at Go; adding both provides little value here. **Why not Python in the core?** Keep the environment and dependency management costs in optional workers and research tooling. **Why not a new DSL?** JSON contracts plus normal code are easier to inspect and integrate.

## 4. Overall architecture and deployment

The Archify diagram is a **logical component map**, not ten independent network services. Its main path is interfaces → run kernel → capability broker → isolated workers. Storage, context, providers, tools and verification are adjacent facilities; responses flow back along the shown relationships.

Local deployment has three process classes:

1. **`runweftd`**: one Rust coordinator per user profile. Owns SQLite, policy, scheduler and effect admission. It has a bounded async runtime and a separate serialized database writer. Rust modules call each other directly inside this process.
2. **Extension hosts**: TypeScript provider and protocol adapters, separated by trust and credential scope and subject to the OS containment contract in §6. They speak versioned JSON-RPC with the coordinator. They cannot write the ledger directly.
3. **Execution workers**: short-lived or leased processes/containers that run commands, browsers, language servers and tests with scoped mounts and networking. They return proposals and artifacts. They cannot self-grant permissions or declare trusted verification.

The Rust CLI talks over an owner-only Unix socket; Windows uses an ACL-protected named pipe. Check peer identity, message sizes and protocol version. The optional web inspector uses a loopback gateway with an ephemeral authenticated session, explicit origin checks and CSRF protection; never expose unauthenticated localhost mutation endpoints. Editor bridges use the same command semantics.

Start **one coordinator per profile**, not one per task or project; isolate workspaces and data scopes inside it. Per-workspace quotas prevent one repository monopolizing the machine. A coordinator crash affects active dispatch but should not destroy accepted state. A worker crash affects that attempt. The initial coordinator is a single point of availability; that is an intentional local-product tradeoff.

No Kafka, Redis, service mesh, or distributed consensus is required initially. Scaling later means replacing a deployment boundary while preserving the command/event contract—not scattering every module into a service.

## 5. Contracts, state and recovery

Core objects: `Run`, `GraphRevision`, `Task`, `Attempt`, `CapabilityGrant`, `BudgetReservation`, `EffectIntent`, `WorkspaceSnapshot`, `Artifact`, `VerificationReceipt`, and `MemoryEntry`. Every persisted object includes a schema version and project/profile scope. Events carry a per-run monotonically increasing sequence, event ID, causation ID, actor, graph revision and policy revision. Wall time is descriptive; event sequence determines replay order.

A task's normal lifecycle is `queued → ready → running → verifying → succeeded`. Alternate states include `awaiting_approval`, `paused`, `failed`, `cancelled`, and `unknown_effect`. Attempts are append-only records underneath the logical task. Retrying creates a new attempt and preserves the previous one. Dependencies require validated outputs, not merely a worker's success text. A changed graph revision invalidates only dependent artifacts according to recorded input digests.

The planner is replaceable and probabilistic. It proposes typed nodes with dependencies, inputs, expected outputs, tools, resource limits and acceptance criteria. A deterministic compiler rejects cycles, undeclared inputs, impossible budgets and privileges outside the parent grant. Amendments create new graph revisions. Repeated revise/retry loops are bounded by attempt, time and spend limits.

SQLite is the local source of truth. In **one transaction**, validate a command against the current revision, append the event, update indexed projections, reserve budget, and enqueue an effect intent. Commit before acknowledging acceptance or dispatching. Use WAL with `synchronous=FULL` for these durable boundaries, foreign keys, unique keys and short transactions. Use a single writer queue with bounded backpressure. Do not store the database on a network filesystem. SQLite WAL permits concurrent readers but a single writer and needs checkpoint management. [SQLite WAL](https://sqlite.org/wal.html).

Large outputs live in a content-addressed artifact directory. Write a temporary object, flush it, atomically rename it and sync its directory before the SQL transaction references its digest. A crash may leave an unreferenced object; garbage collection can remove it after a grace period. A missing referenced artifact is an integrity failure and blocks downstream acceptance. Snapshots accelerate replay; schema migrations and old event readers keep durable history interpretable. Database backup and artifact manifest must represent one consistent high-water mark.

For backup, pin a committed ledger sequence and all artifacts reachable from that snapshot under a GC lease, take a consistent SQLite backup, copy and digest-verify those objects, then publish the manifest atomically. Release the GC lease only after the backup is committed or explicitly abandoned. GC never removes objects reachable from current state, retained checkpoints or active backup leases. Restore verifies the manifest before accepting commands; test backup/GC races and interrupted backups in phase 1.

**Do not promise exactly-once external effects.** The outbox makes dispatch intent durable, but cannot atomically commit with an arbitrary provider or shell process. Classify effects as pure/read-only, idempotent with a remote key, reconcilable by external ID, or non-idempotent/opaque. After a crash, retry reads; reuse supported idempotency keys; query reconcilable effects; put ambiguous opaque effects into `unknown_effect` and require reconciliation before retry. A cancelled request may still have completed externally.

Each admitted attempt gets a lease epoch and fencing token. The local broker rejects effects from an expired epoch, and workers lose credentials/network leases when cancelled. Remote workers require the same check at the actual effect boundary. Do not grant long-lived direct credentials to a remote worker and then pretend a database fence can stop it using them.

Record model request metadata, response artifacts when retention permits, tool outcomes and state transitions. **Replay reconstructs observed execution; it does not reproduce stochastic model output.** Deterministic replay uses recorded responses and tool results. Re-executing against live models is a new run with different provenance.

## 6. Security and authority

Treat repository files, retrieved websites, tool descriptions, model output, skills and third-party extensions as untrusted data. Explicit user grants and administrator policy are authority. A skill asking for a secret or broader permissions cannot change its own grant. Prompt-injection filters may flag suspicious text, but the enforceable boundary is the broker and OS sandbox.

A grant specifies subject/run, workspace roots, allowed tool IDs, operation class, network destinations, permitted secret handles, maximum spend, expiry and delegation ceiling. Effective authority is the intersection of administrator constraints, user grants and narrower task scopes. Project configuration can narrow it; project files cannot elevate it. Child grants are subsets of parent grants. Revocation is checked at each effect admission and closes existing broker leases where possible.

Enforce filesystem access with handles rooted in approved directories and race-resistant path resolution; protect symlinks, traversal, hardlink exposure and mounts. Worktrees protect concurrent edits but do not stop a process reading the user's home directory. External communication goes through scoped egress; separate model-provider access from arbitrary internet access. Credentials remain in the OS credential store or a broker-owned secret service. Prefer broker-side authentication injection so extension code receives no reusable secret.

**Extension containment is mandatory in secure mode.** Every untrusted Node/MCP/other native extension host receives a read-only mount of its verified package/runtime, an empty private temporary directory with a quota, an allowlisted environment without inherited secrets, and only its broker IPC handle. No user-home, ledger, credential-store, arbitrary workspace mounts, daemon management socket, or unrestricted direct network access is available. File/context access and outbound requests require broker handles checked for subject, action, destination and current lease. Apply CPU, memory, process and output limits, and the same platform certification/refusal rules as execution workers. A package's signature does not waive isolation.

When a provider SDK truly requires possession of a credential, put it in a dedicated first-party adapter trust domain, separately audited and contained, with no unrelated context or filesystem access. Give it only a short-lived or least-privileged provider-specific credential and narrowly constrained egress; the broker checks the lease before each request, revokes/terminates the adapter on cancellation, and refuses this route in secure mode if the required enforcement cannot be provided. An in-flight upstream request may still finish and must be reconciled. Credential-bearing adapters remain explicitly in the trusted computing base; no claim of per-call revocation is made for an upstream service that cannot enforce it.

**Data authority follows the data.** Resolving every artifact, memory entry, cached result and context handle requires a read authorization for the receiving subject. Immediately before provider submission, authorize the assembled payload's data scope and destination. Derived summaries inherit the union of their sources' disclosure restrictions (equivalently, the intersection of allowed recipients); neither the model nor a summarizer may declassify them. Delegation, retries, fallback, caching and exports must preserve these labels and recheck the recipient. A child never receives its parent's broader transcript by default. Cache keys include scope and policy revision, and cache hits still pass authorization. Only an explicit authorized user decision can broaden disclosure.

Secure Linux workers use a tested combination of namespaces/mount isolation, restricted syscalls, resource limits and network controls, or a VM for stronger tenant separation. macOS and Windows secure execution initially use a provisioned Linux VM/remote worker if equivalent native enforcement has not passed the conformance suite. A shell with a copied worktree is labelled **trusted-local**, never silently advertised as secure. If secure mode cannot enforce the declared policy, it refuses execution. Reading and planning can remain available.

CodeMode runs without ambient filesystem/network/credential access. It can call broker handles with a per-call identity; batching independent reads is permitted. Writes that share resources are serialized or isolated, then integrated explicitly. Tool-server annotations are hints, not authority. MCP standardizes interchange but does not enforce the application's authorization policy. [MCP specification](https://modelcontextprotocol.io/specification/2025-11-25).

Human approval is needed at defined authority boundaries: newly requested capability, publishing, deployment or other user-designated irreversible action. Routine operations inside a preapproved scope continue automatically. Bind approval to the exact artifact/target/action digest and policy version; a material change invalidates it. The system must not bury new permission requests in a generic “continue” button.

Terminal controls and untrusted HTML are sanitized in viewers. Telemetry defaults to metadata without prompts, source code, screenshots or secret values. Encryption and redaction have explicit limitations: an authorized model endpoint sees submitted context, and a compromised local administrator can generally inspect local processes. These are boundaries to document, not claims a language choice can eliminate.

## 7. Agent orchestration, scheduling and model routing

Keep a **single-agent path** first-class. A five-line fix does not deserve five agents. The graph compiler chooses parallelism only for independent work, with a default local worker cap and explicit global/provider/workspace limits. Admission reserves estimated cost atomically before starting; actual usage settles it, and unknown usage retains a conservative reservation. Rate-limit backoff and circuit breakers are provider-specific and bounded.

Use a ready frontier with critical-path priority plus aging/fairness, rather than global waves that wait for their slowest node. Let a planner propose parallel discovery, implementation and review, but cap delegation depth and total descendants. Results are typed artifact handles plus concise summaries, not indiscriminate copies of every child transcript. Avoid nesting independent orchestration loops across harness adapters.

A model adapter advertises observed capabilities: tool calling, constrained output support, image input, context size, caching, cancellation, authentication mode and usage accounting. Store provider-native details in a versioned extension field. Test those claims against fixtures; an “OpenAI-compatible” endpoint is not assumed semantically identical to every other one.

Routing first applies hard constraints—data destination, tool requirements, context, budget, user preference—then ranks feasible choices by task-specific evaluation results, latency and price. “Cheap” means total cost per accepted result, including retries and verification. Escalate on explicit evidence such as repeated invalid tools, failed tests, or unresolved uncertainty; do not make opaque self-confidence the sole signal. Fallback remains inside the user's provider and data policy. A switch cannot widen context disclosure or authentication scope.

Use versioned role profiles such as planner, implementer, investigator and verifier rather than embedding model names into agent identities. Profiles include prompts, tool grants, budget defaults and evaluation results. Updates can hot-reload for **new attempts**; active attempts keep their pinned policy/config/prompt revision. A run can deliberately migrate with an event, but an update cannot silently change its execution semantics.

## 8. Workspace changes and verification

Capture the starting Git revision plus any authorized uncommitted overlay and relevant untracked files. Do not overwrite the user's active checkout. An implementation attempt writes in a task-owned checkout or snapshot; a read-only investigator can use the same immutable source snapshot. Separate speculative writers where conflicts are possible. Submodules, symlinks, ignored files and large assets require explicit inventory and copy rules.

Use optimistic preconditions on edits: expected content hashes or an AST/LSP operation against an exact document version. This extends the intent of OmO's hash-based edit approach. Before integration, compare the current destination with the recorded base, produce a three-way merge or a reviewable conflict, and never silently discard user changes.

Verification is a policy-driven pipeline: schema/format checks, relevant tests, compilation/type checking where applicable, static/security checks for changed risk, and real UI or integration tests when behavior requires them. Run tests in an environment controlled by the harness; distinguish repository-supplied tests from independent acceptance checks. An agent can edit tests, so a green test log alone is insufficient.

A receipt records artifact digest, source revision, environment/tool versions, commands, exit codes, timestamps, evidence paths, coverage scope and known omissions. Its acceptance decision comes from the coordinator. Recheck the final integrated artifact when integration changes the tested tree; evidence for a previous branch does not approve a different merge result. Review agents read the artifact and evidence independently. They do not receive the implementer's self-assessment as ground truth.

For difficult tasks, support a board with dissent and blocker closure, but do not require a large board on every edit. Consensus is additional evidence, not a substitute for tests or user intent. The main UX distinction is **produced / checked / accepted / published**; “the agent stopped talking” is not a completion criterion.

## 9. Context and memory

Use three explicit layers: transient working context, project knowledge, and opted-in personal preferences. Start retrieval with paths/symbols, lexical search and recency; add embeddings only if a held-out evaluation improves outcome quality enough to pay for indexing and disclosure costs. AST/LSP services remain language-specific tools, not a universal semantic oracle.

Each memory entry includes provenance, workspace/user scope, source digest, observation time, confidence/status and invalidation rules. Branch-specific claims are not silently global. Re-read authoritative files when their digests change. Summaries retain artifact references and unresolved questions; a compressed summary cannot upgrade a guess into a fact.

The memory writer proposes new entries after a run. A deterministic validator checks schema, scope and source presence; user preferences require user-authored or explicitly accepted authority. Memory content cannot grant tool permissions. Data and derived summaries obey §6's read and disclosure checks before storage/retrieval/submission; a memory summary cannot erase a source restriction. Contradictions are preserved with provenance or replaced through an explicit supersession record. Reflection runs consume their own bounded budget.

Store memory records and derived search indexes locally, with Markdown export/import for portability and review. Imported OmO memory becomes attributed, untrusted historical material until validated, not a rewritten user instruction. Opt-in sync must have explicit conflict resolution and secret exclusions. Deletion tombstones propagate to derived indexes, caches and exports under the application's control; document backup-retention limits. Durable logs keep minimal metadata and replaceable/redactable payload references so “append-only” does not mean permanent sensitive-content retention.

## 10. Protocols, plugins and 2027 compatibility

Use **MCP** for tool/resource integration, **LSP** for language intelligence, and **ACP** at the editor boundary where supported. ACP is not the internal scheduler or tool authorization system; its official introduction still describes remote support as work in progress. Pin negotiated protocol versions and maintain conformance fixtures. [ACP introduction](https://agentclientprotocol.com/get-started/introduction).

Internal messages use JSON-RPC and schema-generated bindings. Maintain separate versions for the public API, durable event format, plugin manifest and provider capability profile. Unknown optional fields can be preserved; unknown execution-critical variants fail closed. Set message-size/deadline limits. Stream large data by bounded chunks or artifact handles. Live tokens/activity may be coalesced; accepted state transitions must be replayable by sequence.

Extensions expose typed interception points—before planning, context proposal, before effect, after outcome, before acceptance. They return data and cannot mutate arbitrary runtime objects. Run mandatory policy checks in the coordinator regardless of hook outcome. Deterministic ordering, timeouts, declared resources and pinned versions prevent hidden hook interactions. A failed optional display extension should not stop a task; a failed mandatory authorization check must.

Third-party packages require manifests, digests, origin information, declared grants and uninstall behavior. Installation is not execution authorization. Signatures establish origin/integrity, not benevolence. Start with built-in adapters; defer a public marketplace until permission review, revocation and updates work.

For 2027, prepare for longer-running tasks, new model modalities, changing provider APIs and remote execution through **stable boundaries**, not predictions. Local models can be plugged in through the provider interface, with recorded capability limits. A larger context window does not remove the need for provenance, access controls or deletion. A better model can replace a role without replacing the run engine.

Remote phase: retain one authoritative coordinator for a run. Workers authenticate with mutually authenticated transport and short-lived workload credentials; scope mounts and egress at the worker site. Use heartbeats, leases and fencing, but reconcile effects after disconnect. PostgreSQL and object storage can support a team deployment through the same repository/transaction interfaces. SQLite and PostgreSQL are alternative authorities per deployment; avoid dual-writing to both. No active-active multi-region scheduling in the initial roadmap.

## 11. Observability, distribution and governance

Expose a run timeline showing decisions, grants, pending approvals, attempts, cost reservations, actual usage, evidence and changed artifacts. Allow pause, cancel, branch-from-checkpoint and export. Cancel means “stop future admissions and attempt to terminate running work”; report external effects that could still have completed. UI should show a short outcome and offer deeper evidence, without requiring every developer to understand scheduler internals.

Instrument traces with run/task/attempt IDs using OpenTelemetry, with an internal stable attribute schema mapped to the selected external convention version. Do not make the persistence schema depend directly on evolving GenAI conventions. Log payloads only through scoped opt-in retention. Record model price-table revision and distinguish measured costs from estimates and unknown charges.

Distribute signed native core binaries and a verified, pinned extension runtime bundle. An npm convenience package can download/verify platform assets, but installation should not silently patch another harness's runtime. Ship SBOMs, checksums, rollback metadata and a diagnostics command. Updates first drain or preserve active attempts, back up compatible state, run migrations and health checks, and only then advance the active version. Irreversible data migrations require a supported restore path, not a promise that an older binary can read new data.

Prefer Apache-2.0 for **new, independently authored** core/SDK code and a clear contributor policy. OmO's root license is Sustainable Use License 1.0 with use/distribution restrictions and component exceptions; it is not a blanket permissive grant. Do not copy its implementation, prompts, assets or branding into a presumed permissive commercial successor. Track dependency and copied-content provenance, and resolve component-specific rights before reuse. This is a project constraint, not a legal clearance opinion. [Pinned license text](https://github.com/code-yeongyu/oh-my-openagent/blob/713775cedd533d00c2048ec6dc677f942f3b2ad0/LICENSE.md).

Migration begins with a read-only compatibility inventory for the pinned OmO 5.0.1 source formats, extended only by fixture-backed support for other versions. A dry-run importer maps model preferences, user-owned skills, MCP endpoints and attributed memory into a new profile and reports unsupported keys. It never copies OAuth tokens or silently imports broad grants; credentials are reauthorized and new permissions shown explicitly. Transcripts import as historical artifacts. Active OmO sessions, DAGs, hooks, executable plugins and in-flight effects stay under OmO; no live run transfer or behavioral compatibility is claimed. Run both tools against separate checkouts during a canary period. Rollback selects the untouched OmO installation and its original state, not a reverse conversion of new Runweft runs.

## 12. Build order, falsifiers and acceptance gates

Assume a small team with Rust systems experience and TypeScript integration experience. The following time bands are planning estimates, not commitments. Staff capacity, supported operating systems and provider access determine the schedule.

| Phase | Indicative duration | Deliverable | Exit condition |

**Pre-registered comparison design:** the governing specification is `evaluation-protocol.md` revision EP1, with the delivered `analyze-evaluation.py` research script. Pin the inspected OmO snapshot and exact successor build, task input, permissions and environment. Use 120 held-out tasks (30 each: bug fixes, features, refactors, investigations), five tasks from each of 24 repositories, three attempts per system per task. Freeze the sampling frame, task manifest, independently written acceptance criteria, provider controls and script digest before evaluation. Each paired bootstrap sample draws whole repository clusters, preserving all tasks and repeated attempts, to avoid treating correlated runs as independent. A pilot uses disjoint repositories; imprecise evidence means retaining the incumbent, not repeatedly inspecting a holdout until it passes.

Primary quality metric: proportion of tasks meeting prewritten external acceptance criteria, averaged over attempts per task. Cost metric: total metered API spend over all attempts divided by accepted attempts; report undefined if there are zero acceptances. Also report human intervention minutes, wall-time distributions, cancelled work, CPU/memory and failure taxonomy. Benchmarks use identical model/tool budgets for a harness-only comparison; a separate operational comparison may choose different model routes but must disclose them. Blind adjudicators to system identity where feasible.

**Utility decision rule, in this order:** DIES if a confirmed release-blocking authority escape or silent loss of acknowledged durable state remains. Otherwise WEAKENS if cohort validity, complete spend, or defined cost-ratio requirements fail. Otherwise SURVIVES if the lower interval endpoint for acceptance-rate difference is above −2 percentage points AND either (a) the upper cost-per-accepted-attempt ratio endpoint is below 0.85, or (b) the lower acceptance-difference endpoint is above +5 points and the upper cost-ratio endpoint is below 1.10. Otherwise WEAKENS: no superiority claim and no default migration. EP1 uses 10,000 paired repository-cluster resamples and two 97.5% percentile intervals; Bonferroni targets joint 95% coverage for the two metrics, subject to bootstrap assumptions, rather than treating either branch as a separate unadjusted significance test. These are product thresholds, not results, exact finite-sample guarantees or a power guarantee. API spend is not total cost of ownership; apply the decision with the separately reported local compute and human time.

Operational release targets: zero unauthorized effects in the enumerated policy test suite; zero lost acknowledged transitions across 10,000 injected coordinator crashes; p95 local command acknowledgement below 150 ms at 32 active attempts on a recorded 8-core/16-GB Linux/SSD reference machine, excluding provider latency. EP1 fixes the crash allocation, policy-suite classes, command mix, sample count and percentile calculation; platform manifests and fixture digests are frozen before executing those tests. Missing or failed evidence blocks the associated release claim. Passing a finite suite does not prove absence of vulnerabilities. The goal is auditable evidence, not “100% secure.”

An example run makes the contract concrete. A user requests an API change within a $5 ceiling and permits local testing but not publishing. Runweft snapshots the base and dirty overlay, proposes a graph for investigation, implementation and verification, reserves spend before each model call, and limits two writers to separate checkouts. A child reads only authorized source handles. If the machine restarts after a publish-like external call whose outcome is unknown, that effect cannot be retried automatically; ordinary lost read requests can be. Tests attach receipts to the candidate digest. Integration into a newer base triggers relevant checks again. The user receives an accepted patch with evidence and cost accounting; publishing remains a separate authorized action. The dollar figure is illustrative, not a measured task cost.

A rewrite is not automatically justified. If the new runtime cannot maintain quality or materially improve cost/reliability, contribute compatible pieces or keep using OmO. The architecture should be allowed to fail its own business case.

## 13. Names

1. **Runweft** — preferred working name. “Run” names the durable unit; “weft” suggests separate strands forming one result. Distinctive, provider-neutral, usable as `runweft run`, `runweft inspect`, `runweft resume`.
2. **Relayforge** — emphasizes handing work between specialists and producing engineering artifacts; more forceful but less explicit about verification.
3. **Taskweft** — clear task-graph association, though “task” can sound like a general to-do application.
4. **Keel** — strong reliability metaphor and short command, but generic names are harder to distinguish and may collide.
5. **Prooflane** — emphasizes evidence and progress; avoid implying formal mathematical proof of arbitrary generated code.

These are proposals, not domain/package/trademark clearances. A limited exact-name web search did not establish Runweft's availability. Before launch, check registries, repositories, domains and naming rights in intended markets. The architecture should not depend on the name.
